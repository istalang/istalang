### Performance (P)

Time and memory: measured costs, quadratic paths, hot-path checks.

| # | Item | Size | Depends on | Source |
| --- | --- | --- | --- | --- |
| P1 | Commits dominate the scheduler's cost. Measured in 3.6 (400 executions waiting on one inbox, about 1,200 heap objects, 401 commits): 1.25 s in all, about 3 ms a commit, growing with the square of the executions. About 83% of it is `commit` (scheduler/wake.ts): writing each snapshot through the zod codec and canonical JSON, then reading it back so the next segment restores what a restart would see. Resolving futures, which scans every execution for the ones waiting (scheduler/futures.ts), shows up at a few percent. 3.6 removed the other scans: an execution names its call future, and the heap counts ids up. Options: restore the next segment from the snapshot just written instead of its text, relying on the format's round-trip property (decode after encode is the identity); or write snapshots incrementally. Measure against real workflows first. | big | a benchmark baseline (wake.bench.ts); can start now | phase 2.5 2026-10-25, measured in slice 3.6 |
| P2 | Building a collection one item at a time is quadratic: arrays and maps are immutable plain values, so every append, `push` and `m[k] = v` copies (measured: a 20k-element comprehension ~2.5 s; 5k map inserts ~0.9 s, after each map took over its predecessor's hash table). A spread of anything but the literal's own kind of collection appends item by item through its cursor (§3.10), so `[...0..20000]` takes ~3 s. Persistent structures as the runtime's in-memory representation, or writing in place when a value has one holder, would make it linear. Measure against real workflows first. The prelude's methods taking a function inherit it: `sort`'s merge pushes one item at a time and `Map.groupBy` rebuilds a group and the map per item, as the `map` and `filter` comprehensions build theirs; natives can't call a function value, so none of them can move into a native. | big | choosing persistent collections, with P8; can start now | slice 3.3 2026-10-25 |
| P3 | Proving that what code let go of is unheld walks the live state from the roots, so each such disposal costs as much as the heap is large. Measured on P1's workload (scheduler/wake.bench.ts, 400 workers on one inbox): 0.65 s of 7.1 s is collecting, 4.9 s committing.
