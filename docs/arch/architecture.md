# Architecture

## Shape

- One npm package, `istalang`: ESM, Node ≥ 22, TypeScript 7.0 (stable), vitest + fast-check, Biome 2. M1.1 pins exact versions.
- The build is tsdown (JavaScript, mirroring `src`). Std `.ista` sources are imported as text and compiled into the package, so nothing reads them from disk at run time. Each subpath export is a tsdown entry; its declarations come from TypeScript itself (`tsconfig.declarations.json`, docs/arch/boundary.md, Packages), and a test holds every export to shipping both its JavaScript and its declarations.
- One bin, `ista` (commander), with subcommands `check`, `fmt`, `lsp`, `run` and `test` today; `vendor` and `verify` (M8) are planned.
- Host projects import subpath exports: `istalang/runtime` (the host API) and `istalang/stdlib` (the std natives) today, `istalang/compiler` and `istalang/language-service` later. Each export maps to a real module, never a re-exporting barrel.
- The VS Code extension lives in `.vscode/extensions/ista/`: its manifest, the TextMate grammar (held to the scanner's reserved words by `test/vscode-grammar.test.ts`), and the client of `ista lsp`, which `npm run build` bundles from `src/vscode-client/` into its `dist/`. It is installed from that folder, with no node_modules, so the bundle holds everything but `vscode`; a dependency only the client imports is a devDependency.

## Pipeline

```
text ─scan─▶ tokens ─parse─▶ SyntaxTree ──┐
ModuleLoader(s) ──────────────────────────┴─▶ Program (immutable module-graph snapshot)
Program ─bind─▶ Bindings ─check─▶ types ─lower─▶ Definition (serializable IR)
Definition ─▶ runtime: interpret it over persisted instance snapshots
```

Loading (scan, parse, resolve imports) belongs to `compiler/program/`, because finding a module's imports needs its tree. From a Program onward, `compiler/compile.ts` is the coordinator: it alone knows the phase order, and each phase knows only its input and output.

## Folders (`src/`)

The top level is split by toolchain feature. Inside a phase, folders are split by language construct. No file is longer than 400 lines. A file that grows past that becomes a folder of the same name: `parse.ts` becomes `parse/index.ts`, which keeps the entry's real logic, with the extracted parts beside it.

## Layers

Imports point only downward; cycles are forbidden. Both rules are enforced by lint, not left to review.

```
cli · vscode-client                     the apps (composition roots); nothing imports them. vscode-client
                                        imports of the server only lsp/std-source-request.ts, the request both sides speak
lsp                                     the language server, a composition root that `ista lsp` runs
language-service · formatter · packages tooling; language-service imports no Node built-in
project                                 a project on disk: its sources and the loaders reading them
compiler/compile ─▶ lowering ─▶ checker ─▶ binder ─▶ program ─▶ parser · scanner ─▶ syntax
runtime ─▶ definition ◀─ lowering       runtime never imports compiler/
stdlib ─▶ program (loader seam) · runtime native seam · definition values (==, map keys: definition/equality.ts)
text · diagnostics                      foundation; the runtime may use text/ for positions
language · structures                   beneath every layer; they import nothing
```

- A phase or feature folder is used only through its entry module, which is named for what it does (`scanner/scan.ts`, `parser/parse.ts`). Nothing reaches into another folder's internals. The foundation folders (`text/`, `diagnostics/`) are small vocabularies, used module by module. The checker's surface is its entry and the models it names (`constant-form.ts`, `json-form.ts`, `checked-annotation.ts`, `denotation.ts`, `host-externs.ts`, `types/type.ts`, `types/substitution.ts`, `types/fit.ts`, `types/type-keys.ts`, `types/type-text.ts`, `types/well-known.ts`, `types/instantiation.ts`), which lowering reads module by module.
- Inside the checker, folders are layers too, from the type model up to the constructs: `diagnostics`, `types`, `inference`, `traits`, `resolution`, `calls`, `patterns`, `flow`, `rules`, `declarations`, `closures`, `expressions`, `statements`, `lookup`. A folder imports only those beneath it, so engines never import constructs. Its root modules are its entry, contexts and contracts, which every folder may import, except the classes that wire a body and a program together (`body-checker.ts`, `program-checker.ts`).
- `syntax/` and `definition/` are contracts with high fan-in. Change them deliberately, and update every caller in the same change.
- Mechanisms:
  - Biome `noExcessiveLinesPerFile` enforces the 400-line limit.
  - Biome `noImportCycles` (project domain) forbids cycles.
  - dependency-cruiser enforces the layers as an allow-list over resolved paths (`.dependency-cruiser.mjs`), the checker's inner layers and its surface included. A layer not listed there can import nothing. Biome's import rules match specifiers, whose shape depends on directory depth, so they can't state an allow-list.
  - npm packages may be imported by any layer. Node's built-ins only by apps (`cli/`, `lsp/`) and `project/`, which reads a project's files for both: the layers beneath reach files, processes and clocks through seams. The one exception is `crypto`, which is computation, not I/O: `definition/` hashes content with it, `runtime/` draws an instance's random values (`scheduler/random-source.ts`) and seeds a test's from its title (`testing/run-tests.ts`), and `stdlib/` implements the `crypto` module.

## Phase contracts

| Phase | Signature | Invariants |
| --- | --- | --- |
| source | `createSourceText(path, contents) → SourceText` | The only way to make a SourceText (it is branded). It drops a leading byte order mark, so no phase ever sees one. |
| scan | `scan(source) → { tokens, comments, diagnostics }` | Context-free, total and lossless: never throws, and every character belongs to exactly one token, comment or whitespace run. It emits no INDENT/DEDENT. Tokens carry `firstOnLine`, and columns come from `LineMap`. A template is one token whose `${…}` values keep the tokens scanned for them, each list ending in an `end` token at its `}`; the parser parses each from those, and their comments are among the file's. The result type `ScanResult` lives in `syntax/`, so the parser depends on the contract, not on the scanner. |
| parse | `parse(source, scanned, previous?) → SyntaxTree` | Given the tree of the text before an edit, scans and parses the module whole, then gives every segment whose text is alike, from the start of the line it begins on, the old tree's nodes (`parser/reuse.ts`): a run of items standing in one header, a trait only with all its members, a body only with its function's header, which keeps its node when only its body changed; old runs match new ones by text, in order; the module's own segment, the comments and the diagnostics are the new parse's. Anchors every node's span to the segment being parsed, starting a header segment for each item standing on lines of its own in a module, or in a trait that is a module's item (`ItemRules.headsSegments`), and a body segment for such an item's function body; a position before a header's first token is its start; its own diagnostics stay at text positions. Total: always returns a full tree, with errors as `Missing`/`Invalid` nodes plus diagnostics. It owns layout (indentation blocks, newline-insensitive brackets, `{` as block vs struct literal vs field list), because layout depends on syntactic context. |
| tree | immutable plain objects, discriminated by `kind`, with a `span` anchored to the segment of text it belongs to (`AnchoredSpan`, positions.ts); a `SyntaxTree` holds each function's body apart from its declaration, read through `bodyOf(tree, declaration)`, and where each segment starts (`bases`); `spanIn(tree, span)` (text positions), `extentIn(tree, node)` (the text a node and everything under it cover), `childrenOf(tree, node)` (a function's body last), `fieldChildrenOf(node)` (what the fields hold, a function's body not among them), `parentOf(tree, node)`, `nodesAt(tree, offset)` (root to innermost), `nodesUnder(tree, node)` (it and every node under it, in source order) | Segments are what an edit elsewhere leaves as it is (docs/work/m6-m7/incremental-checking.md §2): a top-level item's header, annotations included, the header of each member on lines of its own of a trait that is a top-level item, the body of a top-level or trait-member function, after its `:` and docstring, and the module's own; lambdas, local functions and initializers stay in the segment around them. A span's offsets count from its segment's start, so spans of different segments never compare, and text positions come only through the tree, where a phase gives them out: diagnostics leaving the binder and checker (`diagnosticIn`), lowering's code writer (`finish(tree)`), the formatter, the language service, `nodesAt` and `visibleAt`. A function's own span covers its header, docstring included, and such a trait's its header up to its members' segments; `extentIn` covers the rest, and a nested function's text is `nestedFunctionSpan`. Children of one segment come in source order by span; those heading segments of their own, a module's items and a trait's members, follow in field order. No parent pointers; parents are derived on demand, memoized per tree, as children are per node. A node holds the offsets of its extent from its start up to its end, not including it, so an empty node holds none. Child traversal is derived generically from node fields, never hand-listed per kind. A node field is therefore a node, a node array, an optional node, or a primitive. A function's body is no field, so a declaration's node, and what is keyed by it, outlives an edit of its body (docs/work/m6-m7/incremental-checking.md §2); traversal takes the tree for it. Checking reads a body as an input it records (`CheckerContext.inputs.bodyOf`), never through the tree, and walks what it reads by `fieldChildrenOf`. Nodes hold no tokens and no resolved references; the binder and checker keep those in side tables. |
| program | `buildProgram({ roots, loaders, roles? }, previous?) → Program { roots, roles, modules: Map<ModuleId, ProgramModule { name, isStd, isTest, tree, imports, diagnostics }> }`, `roles` keyed by `LanguageModule` (language/well-known.ts) | Immutable. Roots arrive located, and so do the std modules the language refers to, by role: the prelude every module sees, `time`, which types duration literals (§2), `json`, whose codecs every value crossing to a host goes through (§9), and `testing`, which only test modules may import (§10); the checker reads them from these roles, never from an id. A loader marks test modules (`isTest`, §10) and the modules the toolchain ships (`isStd`), whose externs need no host. Every loader is asked for every import path, as written; the core imposes no path syntax and does no I/O itself. Its one rule is the language's: a path names exactly one module (distinct ids); otherwise a diagnostic on the path. The core reads a module only when it loads it, once per build, and makes its SourceText. A module id is its source's URL (any scheme), branded and made only from a parsed URL; two paths to one module must yield one id. Building with the previous snapshot reuses every tree whose text is unchanged, by identity, and parses an edited module with its previous tree (parse). `imports` maps each import node to its module. |
| compile | `diagnose(program) → Map<ModuleId, ModuleDiagnostics { source, diagnostics }>`, built from `diagnoseModule(program, module) → ModuleDiagnostics`, which an editor asks per document, `compileProgram(program, entry) → compiled { definition } \| failed \| noMain` | The coordinator's results, memoized per Program: every module's diagnostics from every phase so far, sorted by position, keyed by module id, clean modules included so an editor knows which documents to clear. A shipped (`isStd`) module isn't checked again by every compile; its own tests check it (stdlib/std-modules.test.ts), and what a program uses of it is checked as lowering reads it. A program with any error doesn't compile; `main` is the entry module's `async fn main()` (§9). |
| format | `formatTree(tree) → string \| undefined`, `formatSource(source) → { tree, text }`, `formatText(text) → string \| undefined` (`istalang/formatter`) | Canonical and without options (docs/work/m6-m7/formatter.md): a two-space indent, width 100. A tree with syntax diagnostics is refused (`undefined`), since printing the parser's recovery would rewrite code nobody wrote. The output parses to the same tree (`dump`) with the same comments, and formatting it again changes nothing. It reads only the tree, its comments and its source text: literals print as written, and a multi-line template or docstring is copied whole, its later lines moving with its first only when that keeps its value. Comments are placed on nodes as Prettier places them (`comment-placement.ts`); one no printer emits is an `Unreachable`. A line break is added only between items, before a body, or where it means nothing (`brackets.ts`), so a line holding an import's names or an operator run outside brackets stays as long as it is. |
| workspace | `new Workspace(load: ProgramLoader)`, `write(module, text)`, `close(module)`, `openModules`, `program`, `treeOf(module)`, `diagnosticsOf(module)`; `ProgramLoader = (open, previous) → Program` (language-service/workspace.ts) | The open texts are its one state, an immutable map replaced on every edit; the program is derived from them, loaded once per map, and handed the program before it so unchanged trees are reused. Which roots a project has and where the rest of its texts come from is the app's: the language server's loader (lsp/project-loader.ts) loads what `ista check` loads, with every open file document over its file and among the roots. A document the program doesn't hold (no file: an unsaved buffer, a `std:` module shown read-only) is parsed on its own, once per text, for the features that need syntax alone. |
| navigation | `nameAt(program, module, offset) → NameAt { name, declarations, targets }`, `declarationsOf(checker, module, name) → DeclaredAt[] { declared, at }` (language-service/navigation/declarations.ts); `namesDenoting(program, declaring)`, `referencesAt(program, module, offset) → Reference[]` (references.ts); `renamingAt(program, module, offset)`, `renameEdits(program, module, offset, newName) → Renamed { edits: NameEdit[] } \| Refusal` (rename.ts); `identifierAt(tree, offset)` (language-service/identifier-at.ts), the name inside the offset or ending at it | Every feature reads the checker's identifier query (`lookup.denotationsOf`) and adds where each declaration is declared: its declaring name, which is also how declarations are told apart, by module and offset, since a declaration may be read through copies of its name's node (an async function's own call). A primitive, `Self` and a struct literal's own field have none, so nothing navigates to them. References are every name of the program the query answers with that declaration, std modules included, indexed once per Program. A name acts on its `targets`: the declarations spelled as it is (a conversion's callee acts on its type), and at a shorthand the value it reads or binds, a variable or a function, rather than the field. Rename judges a declaration as its declaring name declares it (an async function's own call as the function), spells a shorthand out, and refuses (human decision, 2026-10-29) a std declaration, a declaration some name denotes together with another (an import naming every overload), a function or field named like a trait member or a function the language calls by name (`main`, the JSON codecs), a parameter named `self`, a new name of either kind, and a new name that isn't one, is `_`, or changes privacy or case. |
| editor queries | `hoverAt`, `signatureHelpAt`, `completionsAt`, `memberCompletionsAt` `(program, module, offset)`; `inlayHintsIn(program, module, span)` (language-service/) | Over the program's checker, for a module the program holds; nothing for one it doesn't. A name is answered through the identifier query (`Checker.lookup.denotationsOf`), so hover agrees with navigation. Hover shows the innermost node at the offset that has a name or a type (a `->` shows the member read), else the name ending there. A function reads as `signatureOf` spells it, in hover, signature help and completion alike. Signature help marks the parameter a resolved call's binding passes the argument to, so a method's receiver never counts; an unresolved call offers its candidates. Completion offers every candidate unfiltered: a member place (after `.`, `?.`, `->`, `?->`, or a qualifier in a type or pattern, written or not) gives the receiver's members, a namespace's exports, or a type's statics and variants; anywhere else, `Bindings.visibleAt` where the name starts, then keywords. Inlay hints type the names a `let`/`const`, a `for` or a lambda leave untyped, except one whose type checking failed to find (the error type). |
| lsp | `serveLanguage(connection, cwd)` (lsp/server.ts); `ista lsp [--stdio]`; the request `ista/source` (`{ uri } → string \| null`) | The project is the client's first workspace folder, else the server's directory. Documents sync whole (`TextDocumentSyncKind.Full`); a document's URI is its module id, a file's read back through its path. Every provider (lsp/providers/) announces its capability and registers its handler together: document symbols, folding ranges, full semantic tokens (legend: language-service/semantic-tokens/semantic-types.ts, no modifiers; one token per line), whole-document formatting by `formatTree`, definition, references, rename (with `prepareRename`, whose refusal reaches the user as a `RequestFailed` error with its reason), hover (Markdown: the code fenced as `ista`, then the docstring), inlay hints, signature help (triggered by `(` and `,`), and completion (triggered by `.` and `>`; on `>`, members alone, so a comparison offers nothing). A position is read by `documentOffset` and a place written by `locationOf` (lsp/locations.ts). A seam is an interface owned by its consumer. Each app's composition root picks the implementations; no module constructs its own collaborators.

## Registries

An open set of handlers is an explicit typed table, assembled in one module and made exhaustive by type. Node-kind and instruction-kind tables alike use `Handlers` from `structures/kind-table.ts`. Adding a node or instruction kind therefore fails compilation until every table over it handles it. Self-registration through import side effects is not used. Tables of this kind:

- parser: prefix and infix parselets by token kind, for expressions, patterns and types; statements and declarations by leading keyword
- operators: one table in `syntax/operators.ts` gives each its level, associativity, meaning (a call of a named function, an ordering through `compare`, built-in equality, short-circuit logic, `??`, membership through `includes`) and the operands it refuses unparenthesized, `**` refusing a prefix directly on its left; comparisons in a row are one `ChainedComparison` node, whose links the checker and lowering read through `comparisonLinksOf` (a single comparison or membership is the one link `comparisonLinkOf` gives); the parser builds its operator parselets from it, and the checker, lowering and flow analysis dispatch on the meaning, so an operator is spelled once
- binder, checker, lowering, formatter, interpreter: one handler per node kind
- LSP providers, CLI commands, std natives, diagnostic catalogs

The handler types of the phases from checking on, which feature slices extend:

| Table | Type | A handler… |
| --- | --- | --- |
| checker expressions | `Handlers<BodyContext, Expression, [expected: Type \| undefined], Type>` | gives the node's type; `expected` guides inference, and `BodyContext.expect` enforces it where the spec says a value must fit |
| checker accepts | `Handlers<BodyContext, Expression, [], Accepts \| undefined>` | for an argument with no type of its own, which the chosen function decides (§3.5), the parameter types it can take, so choosing rules out the rest; undefined for a kind with a type of its own. Composite kinds (tuples, collection literals, branches) recurse through `BodyContext.accepts`. A lambda's result binds the call's type parameters only where the lambda is an argument itself, not inside a composite (D160) |
| checker statements | `Handlers<BodyContext, Statement \| Invalid, [expected: Type \| undefined], Type>` | gives the statement's type: an expression statement's value, `never` for one that leaves, else `unit`; dispatched through `BodyContext.statement` |
| checker declarations | `Handlers<CheckerContext, Declaration, [ModuleId], void>` | resolves what a top-level item declares and checks bodies |
| checker type nodes | `Handlers<Resolution, TypeNode, [], Type>` | gives the type a type node denotes |
| lowering expressions | `Handlers<FunctionContext, Expression, [], Register>` | emits the code and gives the register holding the value |
| lowering statements | `Handlers<FunctionContext, Statement \| Invalid, [], void>` | emits the code |
| interpreter | `{ [Kind in InstructionKind]: (Machine, ActiveFrame, instruction) => void }` | runs the top frame's instruction and moves its pc |

Construct modules reach each other through their context (`BodyContext`, `CheckerContext`, `FunctionContext`, `Machine`), as the parser's categories do through the grammar; a checker folder imports only the folders beneath it (Layers). What one body's rules gather lives in per-concern units the context exposes, each declared in `context.ts` as the narrow interface its consumers use and implemented beside the rules that use it: the checker's `variables`, `functions` (whose current scope gives `returns`, `loops` and asyncness), `implicit` (the calls a construct makes with no call written: `iterate`, `setIndex` for an element written or a map literal's entry, a map literal's `default`, Default's witness, `..=`'s `_inclusiveEnd`, an ordering's `compare` and `in`'s `includes`, an array or range pattern's prelude calls, `x!`'s `panic`, and a template's `toString` and `join`), `collections` (what each collection literal builds), `iterations` (how each iteration runs: through its cursor, or copied whole), `patterns` and `chains`, lowering's `code` (registers, instructions, labels), `variables`, `loops` and `chains`. A feature adds a unit; it doesn't add methods to the context classes. Program-wide, ProgramChecker composes units the same way (top-level constants, the expansion rule), each keeping its results in tables of the checker's entries. Keys for types, and numbers for the identities they are made of, are numbered once for the process (`types/type-keys.ts`, `Checker.typeKeys`), so an object keys alike in every checker; lowering keys its tables by them too, and no number ever reaches a Definition. A value that must fit a type is fitted through `BodyContext.fit`, which `expect` uses and which records its implicit wraps on the node giving the value: an expression, or the `unit` of a bare `return` or of a block with no tail expression (`ValueSite`); a value an assignment writes is fitted through `fitWritten`, and its wraps recorded on its part, whole or destructured; an array literal's spread records one fit for every item it gives, which lowering applies to each as its cursor gives it (a spread needing one is never copied whole); only a map literal spread's keys and values, given together, are fitted through `fitUnwrapped`, which can't wrap; a mismatch decided elsewhere is reported where it is decided: an argument overload choice rejected (`calls/resolve.ts`), a struct target naming another type (`patterns/parts.ts`). Every producer of one value agrees on its type by one rule (`rules/agreement.ts`); `if` and `match` add their branches to it through `rules/branches.ts`. Lowering's totality property (every program that checks clean compiles into a Definition the runtime loads) ties what the checker accepts to what lowering and the runtime take.

Node kinds are PascalCase, so a table keyed by them sits between `biome-ignore-start` and `biome-ignore-end` comments for `useNamingConvention`, and nowhere else is the rule suppressed.

## State: derive, never mirror

Every analysis result is a memoized function of immutable inputs: text → tokens → tree → Program → bindings → types. Caches are keyed by the input object (a `WeakMap`), so a new snapshot is a new key and nothing is ever invalidated by hand. Every one goes through `memo` (`structures/memo.ts`), which remembers an `undefined` too, or `SequenceMemo` for a value derived from a sequence of objects, such as a module's items, except the checker's, which are entries (`structures/entries/`): memoized the same way, and each kept with what it read and reported, so a result never depends on the order things were asked in, and a checker made after an earlier snapshot's takes over every result whose reads answer alike, with nothing invalidated by hand. An entry logs each input read once; replaying it re-reads only those. The LSP holds only document texts and derives everything else. The runtime's only state is the instance snapshot.

## Decisions

- **Hand-written scanner and parser** (Pyright/TypeScript style). Rejected:
  - Langium: its indentation lexer can't turn layout back on for a `{}` block inside `(…)`, and Typir has no generics.
  - Chevrotain, Lezer, tree-sitter: they give untyped CSTs, and context-dependent `{` and generic-call speculation would fight the grammar.
- **No DI container.** Explicit composition roots plus registries keep wiring visible and type-checked.
- **Positions are UTF-16 offsets**, the LSP default. They are converted only at the edges.
- **Formatter layout algorithm comes from a library:** Prettier's doc printer (`prettier/doc`, pinned exactly), which formatter/ alone imports. The formatter supplies only the printers from tree to doc and the comment placement (formatter.md, Decisions).
- **Runtime keeps frames as data.** The Definition is linear register code, so a frame is a function, a pc and registers, and any `await` can be persisted (spec §5). Code is untyped, and generics are compiled per instantiation. The chosen and rejected options are in definition.md, Decisions.
- **One description per persisted format.** A zod schema validates, decodes and encodes it; texts are canonical JSON (lossless-json with sorted keys) nested in a `{format, version, body}` envelope, keyed by content hash. The codec and envelope live in `definition/` (`codec.ts`, `format.ts`), the lowest layer every persisted format already depends on; `runtime/` (snapshots, and from M3 the boundary) imports them from there. Values use `bigint` for `int`.
- **`Decimal` runs on decimal.js,** picked over big.js and bignumber.js because it rounds to significant digits, which `/` needs (34, decimal128's), and has every rounding mode. A `Decimal` is a value of an extern type the `decimal` module declares, whose payload is its canonical text: fields can't be private (spec §3.1), so a struct could be built in a second form, and `==` and map keys would compare forms, not numbers. `time.Zone` is an extern type for the same reason, its payload the zone's canonical IANA id.
- **`regex` runs on re2js,** a pure JavaScript port of RE2: matching is linear in the text, so no pattern can make an instance hang, and RE2's syntax refuses backreferences and lookaround. A regex is its pattern's text, so its compiled program is derived from that text: memoized by it in one bounded, process-wide cache (`lru-cache`).
- **A wait on another instance's end is read from the store** (spec §9). `inst.result()` is a watch future; at each segment start the scheduler resolves it from the watched instance's last commit (scheduler/instance-ends.ts), in every runtime, a test's included, while a test world answers only a test's own waits (`idle()`, `reaches()`), so an outcome is copied snapshot to snapshot and never passes through a host's JSON. What a host must do is only wake the watcher: a waiting `InstanceState` names the instances it watches, and `InstanceGroup` runs a watcher once one of them has ended, after any instance spawned and not yet run. `runtime.isolate` is a spawn with the `terminatesOnPanic` option, kept in the child's snapshot: its panic commits, then terminates it at once, keeping the panic for the `Err`.
- **Methods taking a function are language code.** A native can't call a function value, since a call never re-enters the interpreter, so the prelude's `map`, `filter`, `sort` and the rest are prelude.ista code, and `collections.WeakMap` is the collections module's.
- **Test capabilities are built into the runtime** (spec §10):
  - Every call goes through one call path, where a mock the calling instance holds, or one an instance it descends from holds, replaces its target. A mock is a heap object, so which mock a call reaches is derived from the holder's heap, and releasing a mock brings back the one before it.
  - An instance a test starts calls the test's mocks as it would call a host's extern: the holder runs the replacement inside the caller's segment, and fills the caller's future when a returned future resolves (an `answer` object). One test's instances therefore never share a heap, so `crashEveryAwait` and every snapshot rule hold for them as for any instance. A mock plays the host, in its own instance or another's: a disposable host value it receives or hands back stays a plain host value there, so only the caller owns and disposes it.
  - An advance ends at a commit that answers another instance's call, so the answer arrives, and its caller runs, before the holder goes on; while a caller's segment waits on an answer, no watch sees it idle or at a waypoint.
  - After every commit, the world has each holder drop its answers to calls whose futures the committed caller no longer has (an advance starting `withdrawn`), so what they wait on is let go: a mocked receive that loses a `select` takes nothing, as §6 says.
  - `handle<T>()`, a test's own watches on a spawned instance (`idle()`, `reaches()`) and its reads (`waitingAt()`, `state()`) are runtime capabilities (`NativeTesting`); spawning with `crashEveryAwait` is the production capability `NativeInstances`, as `result()` and `isolate` are. A panic some instance waits for through `result()`, as `expectPanic` does, fails no test. What a test reads of another instance is that instance's last commit, through the test world (scheduler/test-world.ts), which `runtime/testing/` gives each test (and `noTestWorld` refuses outside a test).
  - `ista test` is a CLI command over `runtime/testing/`; the test library is the `testing` std module, written in the language. A suite function is called again in each test's instance, and `_list`/`_run` (testing.ista) are the one place a suite's tests are flattened.
  - A test module sees the private declarations of the modules it imports (binder), so a test can mock a raw extern a module wraps.

## Testing

- vitest with fast-check, with tests colocated as `*.test.ts`.
- Properties check totality and round trips:
  - the scanner is lossless
  - the parser never throws and covers every token
  - the formatter is idempotent and preserves the tree
- Each spec section also gets table-driven valid and invalid inputs.
- `test/corpus/` is shared by every phase. End-to-end tests run through the `ista` CLI.
- A std module's own tests are written in the language, `src/stdlib/<name>/<name>.test.ista`, and `npm run verify` runs them with `ista test src/stdlib` (`npm run test:std`); TypeScript tests cover a native's own logic and compile errors stay corpus cases.
