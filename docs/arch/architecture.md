# Architecture

## Shape

- One npm package, `istalang`: ESM, Node ≥ 22, TypeScript 7.0 (stable), vitest + fast-check, Biome 2. M1.1 pins exact versions.
- The build is tsdown (JavaScript, mirroring `src`). Std `.ista` sources are imported as text and compiled into the package, so nothing reads them from disk at run time. Each subpath export is a tsdown entry; its declarations come from TypeScript itself (`tsconfig.declarations.json`, docs/arch/boundary.md, Packages), and a test holds every export to shipping both its JavaScript and its declarations.
- One bin, `ista` (commander), with subcommands `check`, `run` and `test` today; `fmt` (M6), `lsp` (M7), `vendor` and `verify` (M8) are planned.
- Host projects import subpath exports: `istalang/runtime` (the host API) and `istalang/stdlib` (the std natives) today, `istalang/compiler` and `istalang/language-service` later. Each export maps to a real module, never a re-exporting barrel.
- The VS Code extension lives in `.vscode/extensions/ista/`: today the TextMate grammar only, held to the scanner's reserved words by `test/vscode-grammar.test.ts`. Its LSP client comes with M7.

## Pipeline

```
text ─scan─▶ tokens ─parse─▶ SyntaxTree ──┐
ModuleLoader(s) ──────────────────────────┴─▶ Program (immutable module-graph snapshot)
Program ─bind─▶ Bindings ─check─▶ types ─lower─▶ Definition (serializable IR)
Definition ─▶ runtime: interpret it over persisted instance snapshots
```

Loading (scan, parse, resolve imports) belongs to `compiler/program/`, because finding a module's imports needs its tree. From a Program onward, `compiler/compile.ts` is the coordinator: it alone knows the phase order, and each phase knows only its input and output.

## Folders (`src/`)

The top level is split by toolchain feature. Inside a phase, folders are split by language construct. No file is longer than 400 lines. A file that grows past that becomes a folder of the same name: `parse.ts` becomes `parse/index.ts`, which keeps the entry's real logic, with the extracted parts beside it.

## Layers

Imports point only downward; cycles are forbidden. Both rules are enforced by lint, not left to review.

```
cli · lsp                               apps (composition roots); nothing imports them
language-service · formatter · packages tooling
compiler/compile ─▶ lowering ─▶ checker ─▶ binder ─▶ program ─▶ parser · scanner ─▶ syntax
runtime ─▶ definition ◀─ lowering       runtime never imports compiler/
stdlib ─▶ program (loader seam) · runtime native seam · definition values (==, map keys: definition/equality.ts)
text · diagnostics                      foundation; the runtime may use text/ for positions
language · structures                   beneath every layer; they import nothing
```

- A phase or feature folder is used only through its entry module, which is named for what it does (`scanner/scan.ts`, `parser/parse.ts`). Nothing reaches into another folder's internals. The foundation folders (`text/`, `diagnostics/`) are small vocabularies, used module by module. The checker's surface is its entry and the models it names (`constant-form.ts`, `json-form.ts`, `checked-annotation.ts`, `host-externs.ts`, `types/type.ts`, `types/type-keys.ts`, `types/well-known.ts`, `types/instantiation.ts`), which lowering reads module by module.
- Inside the checker, folders are layers too, from the type model up to the constructs: `diagnostics`, `types`, `inference`, `traits`, `resolution`, `calls`, `patterns`, `flow`, `rules`, `declarations`, `closures`, `expressions`, `statements`. A folder imports only those beneath it, so engines never import constructs. Its root modules are its entry, contexts and contracts, which every folder may import, except the classes that wire a body and a program together (`body-checker.ts`, `program-checker.ts`).
- `syntax/` and `definition/` are contracts with high fan-in. Change them deliberately, and update every caller in the same change.
- Mechanisms:
  - Biome `noExcessiveLinesPerFile` enforces the 400-line limit.
  - Biome `noImportCycles` (project domain) forbids cycles.
  - dependency-cruiser enforces the layers as an allow-list over resolved paths (`.dependency-cruiser.mjs`), the checker's inner layers and its surface included. A layer not listed there can import nothing. Biome's import rules match specifiers, whose shape depends on directory depth, so they can't state an allow-list.
  - npm packages may be imported by any layer. Node's built-ins only by apps: the layers beneath reach files, processes and clocks through seams. The one exception is `crypto`, which is computation, not I/O: `definition/` hashes content with it, `runtime/` draws an instance's random values (`scheduler/random-source.ts`) and seeds a test's from its title (`testing/run-tests.ts`), and `stdlib/` implements the `crypto` module.

## Phase contracts

| Phase | Signature | Invariants |
| --- | --- | --- |
| source | `createSourceText(path, contents) → SourceText` | The only way to make a SourceText (it is branded). It drops a leading byte order mark, so no phase ever sees one. |
| scan | `scan(source) → { tokens, comments, diagnostics }` | Context-free, total and lossless: never throws, and every character belongs to exactly one token, comment or whitespace run. It emits no INDENT/DEDENT. Tokens carry `firstOnLine`, and columns come from `LineMap`. The result type `ScanResult` lives in `syntax/`, so the parser depends on the contract, not on the scanner. |
| parse | `parse(source, scanned) → SyntaxTree` | Total: always returns a full tree, with errors as `Missing`/`Invalid` nodes plus diagnostics. It owns layout (indentation blocks, newline-insensitive brackets, `{` as block vs struct literal vs field list), because layout depends on syntactic context. |
| tree | immutable plain objects, discriminated by `kind`, with a `span` | No parent pointers; parents are derived on demand. Child traversal is derived generically from node fields, never hand-listed per kind. A node field is therefore a node, a node array, an optional node, or a primitive. Nodes hold no tokens and no resolved references; the binder and checker keep those in side tables. |
| program | `buildProgram({ roots, loaders, roles? }, previous?) → Program { roots, roles, modules: Map<ModuleId, ProgramModule { name, isStd, tree, imports, diagnostics }> }`, `roles` keyed by `LanguageModule` (language/well-known.ts) | Immutable. Roots arrive located, and so do the std modules the language refers to, by role: the prelude every module sees, `time`, which types duration literals (§2), `json`, whose codecs every value crossing to a host goes through (§9), and `testing`, which only test modules may import (§10); the checker reads them from these roles, never from an id. A test module is told by its id ending in `.test.ista` (`isTestModule`), the one path rule the core has (D197). A loader marks the modules the toolchain ships (`isStd`), whose externs need no host. Every loader is asked for every import path, as written; the core imposes no other path syntax and does no I/O itself. Its one rule is the language's: a path names exactly one module (distinct ids); otherwise a diagnostic on the path. The core reads a module only when it loads it, once per build, and makes its SourceText. A module id is its source's URL (any scheme), branded and made only from a parsed URL; two paths to one module must yield one id. Building with the previous snapshot reuses every tree whose text is unchanged, by identity. `imports` maps each import node to its module. |
| compile | `diagnose(program) → Map<ModuleId, ModuleDiagnostics { source, diagnostics }>`, `compileProgram(program, entry) → compiled { definition } \| failed \| noMain` | The coordinator's results, memoized per Program: every module's diagnostics from every phase so far, sorted by position, keyed by module id, clean modules included so an editor knows which documents to clear. A shipped (`isStd`) module isn't checked again by every compile; its own tests check it (stdlib/std-modules.test.ts), and what a program uses of it is checked as lowering reads it. A program with any error doesn't compile; `main` is the entry module's `async fn main()` (§9). |
| bind | `bindProgram(program) → Bindings { entityOf(module, name), exportsOf, moduleOf, overloadsOf, candidatesOf, topLevelNamed(module, name), diagnosticsOf }` | Every entity is made while binding one tree, memoized on that tree (`bind-module.ts`): an unchanged module keeps the identity of every entity it declares or refers to across snapshots, and an entity points at its declaring syntax and holds nothing derived. What depends on the whole program is a query memoized per Program: imports, the prelude (the `Program`'s `roles.prelude`), a function set joined with the prelude's overloads (`overloadsOf`), a bare name's candidate variants (`candidatesOf`), what a name denotes at a module's top level (`topLevelNamed`, how operators and method calls find their functions), qualified names. A declaration's or loop's targets are patterns whose names the declaration owns, so its `let` or `const` decides their mutability. A called name no scope defines denotes a function set with no overloads of its own, which argument-dependent lookup may fill; the checker reports it when none is found. Lookups that need types (members, methods, static functions, ADL, picking a variant candidate) are the checker's. |
| check | `checkProgram(program) → Checker { program, bindings, diagnosticsOf(module), moduleOf, parametersOf, resultOf, bodyOf(function) and defaultsOf(function) → CheckedBody { typeOf(expression), calls: site → ResolvedCall, madeCalls() → { site, call }[], implicitCallOf(node, role) → ResolvedCall, collectionFormOf(literal), iterationOf(iteration) → IterationForm { cursor of an item type, or copied whole }, wrapsOf(site), targetsOf(declaration or loop) → TargetBinding[], assignedOf(assignment) → AssignedPart[] { target, path, type, wraps }, inCell(name), functionOf(lambda or local fn) → CheckedFunction { type, parameters, captures }, sourcesOf(literal) → FieldSource[], patternOf(pattern) → CheckedPattern { tests, bindings }, chainOf(link) → ChainLink { base, wraps }, ownCallReadAt(name) and ownCallOf(function) → the hidden variable holding an async function's own call, result }, constantOf(declaration) and constantNamed(module, name) → CheckedConstant { type, form }, constantBodyOf(declaration) → CheckedBody, fieldsOf(type), variantsOf(type), sharedValueOf(type), disposalOf(type), optionalOf(type), cellOf(type), json → { formOf(type), codecOf(type, direction), callOf(name, typeArguments) }, annotations → { of(module, item, place), ofField(field), waypointOf(module, statement) } }`, and `constant-form.ts` (`ConstantForm`, `durationForm`, `formAt`). A `ResolvedCall` is a `function` call (the function, its type arguments, the witnesses of its constraints and how many arguments are given) or a `requirement` call (the function a constraint on the caller's own type parameter requires, by constraint and member index); either names the `receiver` a method call was written on | Memoized per Program and lazy: a body is checked the first time anything needs it (its module's diagnostics, lowering, or inferring a caller's result), so the LSP pays only for what it asks. Binding happens inside: the checker calls the memoized `bindProgram`. A body records each expression's type, each call site's target (calls, operators, compound assignments, indexing, a method call with its receiver, a pattern's `compare`), each call the language makes for a construct with no call written and each value's implicit wraps into `T?` as it is checked, so lowering reads exactly what was checked and never re-derives a type. One walk serves every pattern (`patterns/walk.ts`): a declaration's targets walk it with no tests, so whatever could fail to match is refused, and a `match` case or `is` walks it with tests (`matching.ts`), recording each pattern's tests in the order lowering runs them, its bindings, and a shape for exhaustiveness (`exhaustiveness.ts`, the usefulness algorithm over shapes, free of the checker's types); an assignment's expression targets are taken apart by the same walk (`takeApart`), which reads a tuple or struct target as syntax gives it (`Destructuring`), so only their leaves, places, are the assignment's own (`statements/assignments.ts`); a declaration's targets are recorded as each name's part, by field and element positions, and an assignment's as each place's part, so lowering only reads parts along their paths. How a target, a place and a struct item read as written, parentheses seen through, is syntax's (`destructuringOf`, `targetParts`, `placePath`, `itemName`, `itemValue`), so the parser, binder, checker and lowering read them one way. A variable passed by `&` anywhere in its body, explicitly, as a method's `&self` or as the container whose element is written (its `setIndex` takes it by `&`), or a `let` a closure captures, is recorded as living in a cell (`inCell`), so lowering gives it one. A body's lambdas and local functions are checked inside it, each in a function scope of its own (`closures/functions.ts`: its result, loops and asyncness), so one CheckedBody records them all; a local variable declared outside a nested function is captured by every function between the two, found where names are used (`BodyContext.entityOf`); a top-level name, which the binder gives a module, never is. A name, or a static member, read as a function value is a call site naming the function its closure runs; a call with no resolved site is a call of a function value. A place reaches an element or the value behind a handle (`*x`) through an accessor, a read and a write: changing it reads it and writes it back, an element with `setIndex`, its implicit `write` call, and a handle's value with its cell's instructions, and an assignment ending at one writes it alone (`calls/places.ts`, `lowering/places.ts`). Each link of an optional chain records the type its step works on and whether its chain wraps its value (`chainOf`); which expressions can be links, and what each one's step reads, is syntax's (`chainStepOf`). Lowering reads both and never re-derives a chain's types. An async function's own name before a `.` reads the handle of its enclosing call, a `_Call` whose members are the prelude's, so `worker.disposing()` is an ordinary method call (`closures/own-calls.ts`): the handle is a hidden variable of the function, declared where its name is, which lowering fills at its entry and a nested function captures like any variable. Where each field of a struct or variant literal gets its value is recorded as the literal is checked (`sourcesOf`), by the one rule of which field an item gives (`patterns/struct-items.ts`), which struct targets follow too; lowering and computed constants read the record. A field left to its default (spec §3.1) is recorded as a call to its default's entry: a declaration's fields with a default read as the parameters of a function of their own, called by no name (`syntax/field-defaults.ts`), so a field's type taken from its default, the defaults' body and a default reaching its own field are the parameters' (`declarations/parameters.ts`), and a literal leaving field `i` out calls that function's entry of arity `i`. Every call a body makes, written, implicit or a literal's default, is listed by `madeCalls`, and the functions a module runs code in, its `fn`s and its fields functions, by syntax's `functionsOf`, so the expansion rule (`rules/expansion.ts`) sees a cycle through a default as one through written calls. A generic body is checked once, generically (spec §3.5); the types and calls it records may name its own type parameters, and a call to a constraint's requirement records which requirement, not which function. A function's defaults are checked as one body of their own, each default seeing the parameters before it. A top-level constant is checked the same way, as a value of its own; one walk decides what compile time computes and computes it into a `ConstantForm`, which lowering only maps to a value, as it maps a duration literal's. Who disposes an extern type or a shared struct is derived from the `dispose` declared for it, never listed: a std module's extern one is the runtime's, and any other is found by argument-dependent lookup beside its type, a host's extern `dispose` included (`rules/disposal.ts`). A shared struct (spec §3.18) is a struct declaration marked shared: its fields are no fields of its type (`fieldsOf`), but of the value behind it, an anonymous struct whose origin is the declaration (`sharedValueOf`), so `x.f`, patterns and trait field requirements never see them. `new X{…}` is a struct literal checked against the declared fields, defaults included, whose type is the shared struct and whose spread is a value behind one; `*x` and `x->f` are built in, calling nothing: lowering builds the value with `struct`, makes its cell with `newCell` and reads and writes it with `readCell` and `writeCell`. A use that a `drop` reaches is found by walking the checked body as it runs (`rules/dropped.ts`), by the one model of the order a body's code runs in (`flow/forward.ts`): forward data flow whose rules give states and what names, whole assignments and `drop`s do, while one table, exhaustive by type, says how each expression and statement runs. Where a nested function's body stops running with its holder is syntax's (`nestsFunction`, `bodyChildrenOf`). A type crosses as JSON through its codecs, the witnesses of `Encodable` and `Decodable`: declared functions, or, for a struct, enum, tuple or host type declaring neither, the ones the compiler derives from its form (`rules/json-forms/`), decided once per type, which lowering writes; `codecOf` finds a type's codec, the witness every module finds alike (spec §3.10), where values cross to the host (`use-site.ts`, `toHost`), so a disposable host type has one. An annotation is checked once, where its item stands (`rules/annotations.ts`). Types are `types/type.ts` values: a nominal type is its declaration's binder entity plus type arguments. A refinement narrows a type within the type it widens to (`types/widening.ts`, today a sendable function type): a refined value fits where the wider type is expected, and a `let` without a written type, or producers of one value that disagree, take the widened type. Sendability is asked of a destination (`traits/sendable.ts`): code goes only to another instance (`spawn`), never to the host. The Checker exposes the Program and Bindings it checked: lowering reads module names and sources from the one and resolves names through the other, rather than the checker repeating either surface. |
| lower | `lower(checker, main) → Definition` | Runs only on an error-free program. It compiles what `main` and every startable function reach, each started through a start entry listed in the Definition's `starts` (docs/arch/boundary.md), through a worklist, since generics are compiled per instantiation. An entry is a function instance (`instances.ts`): a declaration, concrete type arguments, the concrete witnesses of its constraints, and how many arguments its callers give, fewer for a generated entry that computes defaults (spec §3.3), or, of the function a declaration's fields read as, for the entry giving field `arity`'s default from the fields before it (spec §3.1). Lowering an instance reads its body through the instance's substitution and closes each call: a requirement becomes the witness the instance was given. A lambda or local function is an entry of its own per owner holding it (`NestedInstance`): an instance of the function whose body declares it, or a top-level constant whose value holds it, which becomes a closure constant of no captures. It is lowered from its owner's body through a `Frame` that lays out its parameters, captures, own name and result, the one a `?` in it returns from (`function-lowering/frames.ts`). Which body an entry reads, and its frame, have that one home: every entry, a start entry's included, is lowered through `instanceLowering` or `nestedLowering` (`function-lowering/`), a start entry's frame naming its header and the call encoding its returns. Every block releases the variables it declared at its end and before a `break` or `continue` leaves it, so a loop body's are fresh each iteration; it keeps its `fn let` variables first. Each pass of a loop, each `if` branch and each `match` or `select` case is a scope of its own, so pattern bindings end with it. A statement releases the temporaries it left at its end, a header (a condition, a `match` subject) before its body (`statements/scopes.ts`). A value the checker wrapped is wrapped once computed, in one place. The Definition is complete: linear register code with no unresolved names and no sugar, one entry per generic instantiation, and every call targeting a function-table entry (definition.md). Names are qualified with each module's canonical `name`, so a Definition and its content hash never depend on where the toolchain ran. An extern's key is built only by `externKey` (`definition/extern-key.ts`): module, name and declared parameter types, module-qualified (`prelude.add(int, float)`, `geometry.place(geometry.Point)`). Every nominal type can be laid out (struct, enum, extern), and an anonymous struct is a nameless struct entry per type (its introducing node plus its fields' types). Code with no syntax behind it is written in `boundary/`: a derived codec's body from its type's derived form, a host extern's wrapper (JSON in and out of its native), and a start entry's JSON edges around the function's own body (`starts.ts`: which functions are startable, and how their arguments and outcome cross). Loading validates indexes, call arity, closure captures, termination and where waiting is allowed, so the interpreter can trust what it reads. |
| run | `createRuntime({ natives, store, now, seed, host? }) → { deploy(text) → { hash, starts, outcome(value), outcomeText(value), start(name, { function?, arguments?, crashEveryAwait? }) }, wake(name), programOf(name), inspect(name), fill(name, token, json), retry(name), terminate(name) }`, an instance named by the host (a name with `/` is the runtime's, for spawned instances); `start` takes the key of a startable function, `main`'s without one, and its arguments as JSON; `start`, `wake`, `fill`, `retry` and `terminate` → `Advanced { state, spawned, logs }`: where the instance stands (an `InstanceState`: ready, waiting until a time and for the end of the instances it names (`watching`, §9), finished with its outcome, panicked, or terminated after a panic, which it keeps), the instances the advance spawned, and the log records its committed segments wrote (§3.8 `log`; a discarded segment's are lost with it, and no snapshot keeps them); `inspect` → `{ state, waitingAt }`, read from the last commit; `settle(wake, first)` drives an instance and everything it spawns, yielding each time to wait until (or undefined when only its host can wake it), resumed with what the host filled meanwhile, and returns how each ended | Deploying reads a Definition's persisted text, binds every extern to a native (a missing one refuses the Definition before anything runs), checks each host extern's declared signature against what the store already holds under its key (§3.6), and stores it by hash. `start` and `wake` advance an instance segment by segment (scheduler/): a driver's `await` ends a segment, which commits through the store before the next runs; an async callee runs eagerly inside its caller's segment. An instance advances from a snapshot, a new one's `unstarted`, so `start` writes nothing before it runs; a segment's spawns are written as `unstarted` instances before its commit, and the host wakes them as it wakes any other. Waking reads the snapshot and its Definition from the store and checks one against the other before restoring. The runtime holds no timers: a waiting state names when its earliest timer is due, and the host wakes it then (`settle.ts` is that loop, for a host that waits its own way). An instance's options, set at `start`, are kept in its snapshot, so a fresh runtime honours them. An `InstanceState` is derived from the last commit alone. A refusal is a `Refusal` (`runtime/refusal.ts`); with the FormatError of an invalid or unknown-version text, it is all a host catches. A broken invariant, a bug in the toolchain, is an `Unreachable` (`structures/unreachable.ts`) in every phase, so a host tells it from its own mistakes. Every call goes through the function table, after the mock its instance reaches, if one replaces the function (scheduler/mocks.ts); `outcome` gives an outcome a start entry encoded as the JSON a host works with, every integer a `bigint` as in every other exchange, and `outcomeText` gives its JSON text (§9), whose object keys a JavaScript object can't keep sorted. JSON a host gives is checked by compiled code, inside the call that gave it: what doesn't fit refuses a `start` or `fill`, with nothing committed, and panics the instance when it is an extern's result. An extern constant is read once per instance and pinned in its snapshot. `retry` re-runs a panicked instance's failed segment at the time it first started; `terminate` ends it, disposing everything its last commit held. A fill naming no future the instance waits on changes nothing. |

Sugar is split by whether it has typing consequences:
- **Resolved in the checker** (it affects types or diagnostics): default parameters become overloads (and a clash is an error); `T?` is `Optional<T>`, and where a value is wrapped into it; operators, indexing, `for` and `T(x)` become resolved function calls; trait-constrained calls become requirement calls; compound index assignment requires a `let`; closure captures become cells (`_Cell<T>`).
- **Done mechanically in lowering**, following the checker's decisions: overload bodies (default entries), wraps, instantiation, capture structs, `defer` guards, `?.`/`??`/`is` as `match`, comprehensions as loops.

Each phase returns its diagnostics as values; there is no global sink. Codes are unique, with one catalog per phase.

## Seams and composition

A seam is an interface owned by its consumer. Each app's composition root picks the implementations; no module constructs its own collaborators.

| Seam | Owner | Implementations |
| --- | --- | --- |
| `ModuleLoader` | program | `(path, importer) → { id, name, label, read(), isStd? } \| undefined`: locates the module the string in an import names, without reading it. `name` is the module's canonical name, the import path that names it from anywhere (`purchase/approve`, `time`), which compiled code is qualified with; `label` is how diagnostics show it, and may depend on where the toolchain runs; the core calls `read` once, when it loads the module. Implementations: the project's files (`cli/file-loader.ts`, which owns the toolchain's path syntax, §3.13), the std modules (`stdlib/stdlib-loader.ts`, simple names, embedded sources), later vendored packages and an editor overlay, in-memory (tests). A host may pass any loaders of its own. Every loader answers every path: two different modules for one path is an error, and when two locate the same module the first one is used, so an overlay that must win is listed first. |
| `InstanceStore` | runtime | in memory (tests, `ista run`), a directory (`ista run --store`, atomic by rename), or host-provided persistence. It keeps texts: each Definition once, by content hash, which an instance references for its whole life, and each instance's last snapshot by name. Definitions and snapshots both carry a format version; in v0.1 the runtime refuses any version it doesn't know. |
| `Natives` (extern bindings by module-qualified name) | runtime | stdlib natives (`stdlib/natives.ts`), host externs (the `host` seam: written against JSON, adapted by `runtime/boundary/host-natives.ts`; `ista run --host <module>` loads them from a module), test mocks. Each call gets a context (`runtime/natives.ts`): the extern's name, the type entries its declared result and type arguments name (read there, never by narrowing the function entry), the Definition's types, the calling instance's name and the content hash of the Definition it runs, the segment's start time, the trace of the frames running it, and a `write` for each argument the extern takes by `&`; and capabilities, one per part of the instance a native reaches, each a member of the context (`context.futures`): futures (already resolved, `first`, a timer, one its host fills later by a token), slots, weak references, resources, the random source (a draw) and the log (a record, reaching the host with its segment's commit), and what a test reaches. The runtime builds them once per segment and gives every native every capability; a native or a table of them is typed by the ones it uses (`Native<Context>`, `Natives<Context>`), so a table needing one the runtime lacks doesn't compile. |
| `now` | runtime | the host's clock in milliseconds since the epoch: each segment's start, which `time.now()` returns and which due timers are resolved against. The host wakes an instance when its waiting state says its earliest timer is due; `ista run` sleeps until then. Programs fake time only through `mock(time.at, …)` (§10), not through this seam. |
| `seed` | runtime | the host's entropy: a new secret seed, `seedBytes` random bytes (`runtime/random-seed.ts`, which also keeps a seed's text in a snapshot), for each instance it starts, refused at `start` when it has another length, the source of its random values (§3.8 `random`); a spawned instance's is drawn from its parent's, and a test's is made from its title. Log records need no seam: they reach the host in `Advanced.logs` |

## Registries

An open set of handlers is an explicit typed table, assembled in one module and made exhaustive by type. Node-kind and instruction-kind tables alike use `Handlers` from `structures/kind-table.ts`. Adding a node or instruction kind therefore fails compilation until every table over it handles it. Self-registration through import side effects is not used. Tables of this kind:

- parser: prefix and infix parselets by token kind, for expressions, patterns and types; statements and declarations by leading keyword
- operators: one table in `syntax/operators.ts` gives each its level, associativity, meaning (a call of a named function, an ordering through `compare`, built-in equality, short-circuit logic, `??`, membership) and the operands it refuses unparenthesized; the parser builds its operator parselets from it, and the checker, lowering and flow analysis dispatch on the meaning, so an operator is spelled once
- binder, checker, lowering, formatter, interpreter: one handler per node kind
- LSP providers, CLI commands, std natives, diagnostic catalogs

The handler types of the phases from checking on, which feature slices extend:

| Table | Type | A handler… |
| --- | --- | --- |
| checker expressions | `Handlers<BodyContext, Expression, [expected: Type \| undefined], Type>` | gives the node's type; `expected` guides inference, and `BodyContext.expect` enforces it where the spec says a value must fit |
| checker accepts | `Handlers<BodyContext, Expression, [], Accepts \| undefined>` | for an argument with no type of its own, which the chosen function decides (§3.5), the parameter types it can take, so choosing rules out the rest; undefined for a kind with a type of its own. Composite kinds (tuples, collection literals, branches) recurse through `BodyContext.accepts`. A lambda's result binds the call's type parameters only where the lambda is an argument itself, not inside a composite (D160) |
| checker statements | `Handlers<BodyContext, Statement \| Invalid, [expected: Type \| undefined], Type>` | gives the statement's type: an expression statement's value, `never` for one that leaves, else `unit`; dispatched through `BodyContext.statement` |
| checker declarations | `Handlers<CheckerContext, Declaration, [ModuleId], void>` | resolves what a top-level item declares and checks bodies |
| checker type nodes | `Handlers<Resolution, TypeNode, [], Type>` | gives the type a type node denotes |
| lowering expressions | `Handlers<FunctionContext, Expression, [], Register>` | emits the code and gives the register holding the value |
| lowering statements | `Handlers<FunctionContext, Statement \| Invalid, [], void>` | emits the code |
| interpreter | `{ [Kind in InstructionKind]: (Machine, ActiveFrame, instruction) => void }` | runs the top frame's instruction and moves its pc |

Construct modules reach each other through their context (`BodyContext`, `CheckerContext`, `FunctionContext`, `Machine`), as the parser's categories do through the grammar; a checker folder imports only the folders beneath it (Layers). What one body's rules gather lives in per-concern units the context exposes, beside the rules that use them: the checker's `variables`, `functions` (whose current scope gives `returns`, `loops` and asyncness), `implicit` (the calls a construct makes with no call written: `iterate`, `setIndex` for an element written or a map literal's entry, a map literal's `default`, Default's witness, and `..=`'s `add`), `collections` (what each collection literal builds), `iterations` (how each iteration runs: through its cursor, or copied whole), `patterns`, `chains` and `ownCalls` (the call an async function's own name reads), lowering's `code` (registers, instructions, labels), `variables`, `loops` and `chains`. A feature adds a unit; it doesn't add methods to the context classes. Program-wide, ProgramChecker composes units the same way (top-level constants, the expansion rule), and the lazy, cycle-reporting check of bodies and constants is one (`lazy-checks.ts`). Keys for types, and numbers for the identities they are made of, belong to the checker (`Checker.typeKeys`), which lowering keys its tables by too; nothing keeps a module-global counter. A value that must fit a type is fitted through `BodyContext.fit`, which `expect` uses and which records its implicit wraps on the node giving the value: an expression, or the `unit` of a bare `return` or of a block with no tail expression (`ValueSite`); a value an assignment writes is fitted through `fitWritten`, and its wraps recorded on its part, whole or destructured; only a spread's items, given as a whole, are fitted through `fitUnwrapped`, which can't wrap; a mismatch decided elsewhere is reported where it is decided: an argument overload choice rejected (`calls/resolve.ts`), a struct target naming another type (`patterns/parts.ts`). Every producer of one value agrees on its type by one rule (`rules/agreement.ts`); `if` and `match` add their branches to it through `rules/branches.ts`. A construct not supported yet shares one entry per table: the checker reports it (`notSupportedYet`, code 5000), and lowering and the interpreter refuse it. The checker is the one frontier: it also reports what lowering, the natives or the boundary can't take yet. Lowering's totality property (every program that checks clean compiles into a Definition the runtime loads) holds the two together. A feature slice replaces its kinds' entries and moves the frontier.

Node kinds are PascalCase, so a table keyed by them sits between `biome-ignore-start` and `biome-ignore-end` comments for `useNamingConvention`, and nowhere else is the rule suppressed.

## State: derive, never mirror

Every analysis result is a memoized function of immutable inputs: text → tokens → tree → Program → bindings → types. Caches are keyed by the input object (a `WeakMap`), so a new snapshot is a new key and nothing is ever invalidated by hand. Every one goes through `memo` (`structures/memo.ts`), which remembers an `undefined` too. The LSP holds only document texts and derives everything else. The runtime's only state is the instance snapshot.

## Decisions

- **Hand-written scanner and parser** (Pyright/TypeScript style). Rejected:
  - Langium: its indentation lexer can't turn layout back on for a `{}` block inside `(…)`, and Typir has no generics.
  - Chevrotain, Lezer, tree-sitter: they give untyped CSTs, and context-dependent `{` and generic-call speculation would fight the grammar.
- **No DI container.** Explicit composition roots plus registries keep wiring visible and type-checked.
- **Positions are UTF-16 offsets**, the LSP default. They are converted only at the edges.
- **Formatter layout algorithm comes from a library** (a Wadler-style doc printer such as Prettier's). Which one is decided at the formatter milestone.
- **Runtime keeps frames as data.** The Definition is linear register code, so a frame is a function, a pc and registers, and any `await` can be persisted (spec §5). Code is untyped, and generics are compiled per instantiation. The chosen and rejected options are in definition.md, Decisions.
- **One description per persisted format.** A zod schema validates, decodes and encodes it; texts are canonical JSON (lossless-json with sorted keys) nested in a `{format, version, body}` envelope, keyed by content hash. The codec and envelope live in `definition/` (`codec.ts`, `format.ts`), the lowest layer every persisted format already depends on; `runtime/` (snapshots, and from M3 the boundary) imports them from there. Values use `bigint` for `int`.
- **`Decimal` runs on decimal.js,** picked over big.js and bignumber.js because it rounds to significant digits, which `/` needs (34, decimal128's), and has every rounding mode. A `Decimal` is a value of an extern type the `decimal` module declares, whose payload is its canonical text: fields can't be private (spec §3.1), so a struct could be built in a second form, and `==` and map keys would compare forms, not numbers. `time.Zone` is an extern type for the same reason, its payload the zone's canonical IANA id.
- **`regex` runs on re2js,** a pure JavaScript port of RE2: matching is linear in the text, so no pattern can make an instance hang, and RE2's syntax refuses backreferences and lookaround. A regex is its pattern's text, so its compiled program is derived from that text: memoized by it in one bounded, process-wide cache (`lru-cache`).
- **A wait on another instance's end is read from the store** (spec §9). `inst.result()` is a watch future; at each segment start the scheduler resolves it from the watched instance's last commit (scheduler/instance-ends.ts), in every runtime, a test's included, while a test world answers only a test's own waits (`idle()`, `reaches()`), so an outcome is copied snapshot to snapshot and never passes through a host's JSON. What a host must do is only wake the watcher: a waiting `InstanceState` names the instances it watches, and `InstanceGroup` runs a watcher once one of them has ended, after any instance spawned and not yet run. `runtime.isolate` is a spawn with the `terminatesOnPanic` option, kept in the child's snapshot: its panic commits, then terminates it at once, keeping the panic for the `Err`.
- **Methods taking a function are language code.** A native can't call a function value, since a call never re-enters the interpreter, so the prelude's `map`, `filter`, `sort` and the rest are prelude.ista code, and `collections.WeakMap` is the collections module's.
- **Test capabilities are built into the runtime** (spec §10):
  - Every call goes through one call path, where a mock the calling instance holds, or one an instance it descends from holds, replaces its target. A mock is a heap object, so which mock a call reaches is derived from the holder's heap, and releasing a mock brings back the one before it.
  - An instance a test starts calls the test's mocks as it would call a host's extern: the holder runs the replacement inside the caller's segment, and fills the caller's future when a returned future resolves (an `answer` object). One test's instances therefore never share a heap, so `crashEveryAwait` and every snapshot rule hold for them as for any instance. The holder plays the host: a disposable host value it receives or hands back stays a plain host value there, so only a caller in another instance owns and disposes it (a caller in the holder's own instance holds it plain too, D182).
  - An advance ends at a commit that answers another instance's call, so the answer arrives, and its caller runs, before the holder goes on; while a caller's segment waits on an answer, no watch sees it idle or at a waypoint.
  - After every commit, the world has each holder drop its answers to calls whose futures the committed caller no longer has (an advance starting `withdrawn`), so what they wait on is let go: a mocked receive that loses a `select` takes nothing, as §6 says.
  - `handle<T>()`, a test's own watches on a spawned instance (`idle()`, `reaches()`) and its reads (`waitingAt()`, `state()`) are runtime capabilities (`NativeTesting`); spawning with `crashEveryAwait` is the production capability `NativeInstances`, as `result()` and `isolate` are. A panic some instance waits for through `result()`, as `expectPanic` does, fails no test. What a test reads of another instance is that instance's last commit, through the test world (scheduler/test-world.ts), which only `runtime/testing/` gives.
  - `ista test` is a CLI command over `runtime/testing/`; the test library is the `testing` std module, written in the language. A suite function is called again in each test's instance, and `_list`/`_run` (testing.ista) are the one place a suite's tests are flattened.
  - A test module sees the private declarations of the modules it imports (binder), so a test can mock a raw extern a module wraps.

## Testing

- vitest with fast-check, with tests colocated as `*.test.ts`.
- Properties check totality and round trips:
  - the scanner is lossless
  - the parser never throws and covers every token
  - the formatter is idempotent and preserves the tree
- Each spec section also gets table-driven valid and invalid inputs.
- `test/corpus/` is shared by every phase. End-to-end tests run through the `ista` CLI.
- A std module's own tests are written in the language, `src/stdlib/<name>/<name>.test.ista`, and `npm run verify` runs them with `ista test src/stdlib` (`npm run test:std`); TypeScript tests cover a native's own logic and compile errors stay corpus cases.
