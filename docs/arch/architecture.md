# Architecture

## Shape

- One npm package, `istalang`: ESM, Node ≥ 22, TypeScript 7.0 (stable), vitest + fast-check, Biome 2. M1.1 pins exact versions.
- The build is tsdown (JavaScript, mirroring `src`). Std `.ista` sources are imported as text and compiled into the package, so nothing reads them from disk at run time. Each subpath export is a tsdown entry; its declarations come from TypeScript itself (`tsconfig.declarations.json`, docs/arch/boundary.md, Packages), and a test holds every export to shipping both its JavaScript and its declarations.
- One bin, `ista` (commander), with subcommands `check`, `fmt`, `lsp`, `run` and `test` today; `vendor` and `verify` (M8) are planned.
- Host projects import subpath exports: `istalang/runtime` (the host API) and `istalang/stdlib` (the std natives) today, `istalang/compiler` and `istalang/language-service` later. Each export maps to a real module, never a re-exporting barrel.
- The VS Code extension lives in `.vscode/extensions/ista/`: its manifest (whose `[ista]` defaults turn word-based suggestions off, so a place the server leaves empty shows nothing), the language configuration (its word pattern held to the scanner's identifiers by completion's VC-03), the TextMate grammar (held to the scanner's reserved words by `test/vscode-grammar.test.ts`), and the client of `ista lsp`, which `npm run build` bundles from `src/editor/vscode-client/` into its `dist/`. It is installed from that folder, with no node_modules, so the bundle holds everything but `vscode`; a dependency only the client imports is a devDependency.

## Pipeline

```
text ─scan─▶ tokens ─parse─▶ SyntaxTree ──┐
ModuleLoader(s) ──────────────────────────┴─▶ Program (immutable module-graph snapshot)
Program ─bind─▶ Bindings ─check─▶ types ─lower─▶ Definition (serializable IR)
Definition ─▶ runtime: interpret it over persisted instance snapshots
```

Loading (scan, parse, resolve imports) belongs to `compiler/program/`, because finding a module's imports needs its tree. From a Program onward, `compiler/compile.ts` is the coordinator: it alone knows the phase order, and each phase knows only its input and output.

## Folders (`src/`)

The top level is split by toolchain feature. Inside a phase, folders are split by language construct. No file is longer than 400 lines. A file that grows past that becomes a folder of the same name: `parse.ts` becomes `parse/index.ts`, which keeps the entry's real logic, with the extracted parts beside it.

## Layers

Imports point only downward; cycles are forbidden. Both rules are enforced by lint, not left to review.

```
cli · editor/vscode-client              the apps (composition roots); nothing imports them. vscode-client
                                        imports of the server only editor/lsp/std-source-request.ts, the request both sides speak
editor/lsp                              the language server, a composition root that `ista lsp` runs
editor/language-service · formatter     tooling, with packages; language-service imports no Node built-in
project                                 a project on disk: its sources and the loaders reading them
compiler/compile ─▶ lowering ─▶ checker ─▶ binder ─▶ program ─▶ parser · scanner ─▶ syntax
runtime ─▶ definition ◀─ lowering       runtime never imports compiler/
stdlib ─▶ program (loader seam) · runtime native seam · definition values (==, map keys: definition/values/equality.ts)
foundation/text · diagnostics           vocabularies every phase uses; the runtime may use text/ for positions
foundation/language · structures        beneath every layer; they import nothing
```

- A phase or feature folder is used only through its entry module, which is named for what it does (`scanner/scan.ts`, `parser/parse.ts`). Nothing reaches into another folder's internals. The foundation folders (`foundation/text/`, `foundation/diagnostics/`, …) are small vocabularies, used module by module. The checker's surface is its entry and the models it names (`surface/`, `types/type/index.ts`, `types/type/primitives.ts`, `types/type/alias-uses.ts`, `types/type/computed-types.ts`, `types/type/function-types.ts`, `types/type/function-kinds.ts`, `types/type/field-order.ts`, `types/identity/identity.ts`, `types/identity/unfolding-pairs.ts`, `types/written/named-types.ts`, `types/written/pattern-types.ts`, `types/parts/substitution.ts`, `types/type/type-rules.ts`, `types/fitting/fit/index.ts`, `types/fitting/part-pairs.ts`, `types/fitting/expected.ts`, `types/unions/unions.ts`, `types/unions/union-members.ts`, `types/identity/recursive-types.ts`, `types/identity/folding.ts`, `types/identity/type-keys.ts`, `types/type/type-text.ts`, `types/type/well-known.ts`), which lowering reads module by module.
- Inside the checker, folders are layers too, from the type model up to the constructs: `diagnostics`, `types` (the model, then `types/inference`, then `types/traits`), `resolution` (then `resolution/calls`), `rules` (`rules/flow`, then the rest), `constructs` (`patterns`, `loops`, `declarations`, `closures`, `expressions`, `statements`), `lookup`. A folder holding several layers is a contiguous run of them, so it is a layer as a whole too. A layer imports only those beneath it, so engines never import constructs. Its contracts, its entry, `contexts/` and `surface/` (the models later phases read), may be imported by every folder; they import nothing above the type model, but the body's contract (`contexts/body-context.ts`, `contexts/scopes.ts`), which names inference too, whose system of variables a constraint scope is, and which the type model and inference never import. `wiring/` (the modules that wire a body and a program together) imports every layer, and nothing imports it.
- `syntax/` and `definition/` are contracts with high fan-in. Change them deliberately, and update every caller in the same change.
- Mechanisms:
  - Biome `noExcessiveLinesPerFile` enforces the 400-line limit.
  - Biome `noImportCycles` (project domain) forbids cycles.
  - dependency-cruiser enforces the layers as an allow-list over resolved paths (`.dependency-cruiser.mjs`), the checker's inner layers and its surface included. A layer not listed there can import nothing. Biome's import rules match specifiers, whose shape depends on directory depth, so they can't state an allow-list.
  - npm packages may be imported by any layer. Node's built-ins only by apps (`cli/`, `editor/lsp/`, `editor/vscode-client/`) and `project/`, which reads a project's files for both: the layers beneath reach files, processes and clocks through seams. The one exception is `crypto`, which is computation, not I/O: `definition/` hashes content with it, `runtime/` draws an instance's random values (`snapshot/random.ts`) and seeds a test's from its title (`testing/run-tests.ts`), and `stdlib/` implements the `crypto` module.

Sugar is split by whether it has typing consequences:
- **Resolved in the checker** (it affects types or diagnostics): a call's arguments are bound to its function's parameters, each one left out to its default, a call through a requirement to the required function's, which its witness's binding then maps onto its own (and an overload clash is an error); `T?` is `T | None`, and where a value is put into a union, as which member; operators, indexing, `for` and `T(x)` become resolved function calls; trait-constrained calls become requirement calls; compound index assignment requires a `let`; closure captures become cells (`_Cell<T>`).
- **Desugared by the checker** (its core tree depends on types, `checker/desugaring/`): `a!` is `a ?? panic("Force-unwrapped none.")`; a deferred call `g f(x)` is `g` called with, given after its arguments, `{ const v = x; fn(): f(v) }`, a value computed now typed as a constant's is. The core is checked where the sugar is written and recorded (`CheckedBody.coreOf`); flow, lowering, the rules and tools read it, and no later phase knows the sugar.
- **Done in a body's flow** (`checker/rules/flow/build/`, which lowering writes from), following the checker's decisions: `?.`/`??`/`is` as branches, comprehensions as loops, a struct literal's defaults as its fields function's call. **Done mechanically in lowering**: overload bodies (a prologue computing their defaults), conversions into unions, instantiation, capture structs.

Each phase returns its diagnostics as values; there is no global sink. Codes are unique, with one catalog per phase.

## Seams and composition

A seam is an interface owned by its consumer. Each app's composition root picks the implementations; no module constructs its own collaborators.

## Registries

An open set of handlers is an explicit typed table, assembled in one module and made exhaustive by type. Node-kind and instruction-kind tables alike use `Handlers` from `foundation/structures/kind-table.ts`. Adding a node or instruction kind therefore fails compilation until every table over it handles it. Self-registration through import side effects is not used. Tables of this kind:

- parser: prefix and infix parselets by token kind, for expressions, patterns and types; statements and declarations by leading keyword; a contextual word's in a table by its text. The words each table takes are its position's list in `syntax/tokens/grammar-words.ts`, which it `satisfies` both ways (parser/grammar/word-parselets.ts), and which completion offers, so a word is listed once
- operators: one table in `syntax/expressions/operators.ts` gives each its level, associativity, meaning (a call of a named function, an ordering through `compare`, built-in equality, short-circuit logic, `??`, membership through `includes`) and the operands it refuses unparenthesized, `**` refusing a prefix directly on its left; comparisons in a row are one `ChainedComparison` node, which the checker desugars (`checker/desugaring/chained-comparisons.ts`) into its links joined by `and`, so every phase after checking meets one comparison at a time (`isComparison`); the parser builds its operator parselets from it, and the checker and the flow builder dispatch on the meaning, so an operator is spelled once
- binder, checker, flow builder, formatter: one handler per node kind; lowering, one writer per flow operation and exit; interpreter, one handler per instruction kind
- completion: one provider per place kind, one presenter per subject kind (editor/language-service/completion/)
- LSP providers, CLI commands, std natives, diagnostic catalogs

The handler types of the phases from checking on, which feature slices extend:

| Table | Type | A handler… |
| --- | --- | --- |
| checker expressions | `Handlers<BodyContext, Expression, [expected: Type \| undefined], Type>` | gives the node's type; `expected` guides inference, and `BodyContext.expect` enforces it where the spec says a value must fit |
| checker statements | `Handlers<BodyContext, Statement \| Invalid, [expected: Type \| undefined], Type>` | gives the statement's type: an expression statement's value, `Never` for one that leaves, else `Unit`; dispatched through `BodyContext.statement` |
| checker declarations | `Handlers<CheckerContext, Declaration, [ModuleId], void>` | resolves what a top-level item declares and checks bodies |
| checker type nodes | `Handlers<Resolution, TypeNode, [], Type>` | gives the type a type node denotes |
| lowering operations | `{ [Op in Operation['op']]: (FlowWriter, Op) => void }` | writes a flow operation's instructions |
| lowering exits | `{ [Kind in Exit['kind']]: (FlowWriter, Kind) => void }` | writes how a flow block ends, a branch's test by kind |
| interpreter | `{ [Kind in InstructionKind]: (Machine, ActiveFrame, instruction) => void }` | runs the top frame's instruction and moves its pc |

Construct modules reach each other through their context (`BodyContext`, `CheckerContext`, `FunctionContext`, `Machine`), as the parser's categories do through the grammar; a checker folder imports only the folders beneath it (Layers). What one body's rules gather lives in per-concern units the context exposes, each declared in `body-context.ts` as the narrow interface its consumers use and implemented beside the rules that use it: the checker's `variables`, `functions` (whose current scope gives `returns`, `loops` and asyncness), `implicit` (the calls a construct makes with no call written: `iterate`, `onAwait` for what an `await` or a `select` case waits on, `setIndex` for an element written or a map literal's entry, a map literal's `default`, Default's witness, an ordering's `compare` and `in`'s `includes`, and an array or range pattern's prelude calls), `collections` (what each collection literal builds), `iterations` (how each iteration runs: through its cursor, or copied whole), `valueCalls` (the calls of function values), `patterns` and `chains`, lowering's `code` (registers, instructions, labels) and `variables`. A feature adds a unit; it doesn't add methods to the context classes. Program-wide, ProgramChecker composes units the same way (top-level constants, the expansion rule), each keeping its results in tables of the checker's entries. Keys for types, and numbers for the identities they are made of, are numbered once for the process (`types/identity/type-keys.ts`, `Checker.typeKeys`), so an object keys alike in every checker; lowering keys its tables by them too, and no number ever reaches a Definition. A value that must fit a type is fitted through `BodyContext.fit`, which `expect` uses and which records its implicit wraps on the node giving the value: an expression, or the `Unit` of a bare `return` or of a block with no tail expression (`ValueSite`); a value an assignment writes is fitted through `fitWritten`, and its wraps recorded on its part, whole or destructured; an array literal's spread records one fit for every item it gives, which its flow applies to each as its cursor gives it (a spread needing one is never copied whole), and a map literal's spread one for every `(key, value)` pair, settled once the literal's keys and values agree (`constructs/expressions/collections/literals.ts`); a mismatch decided elsewhere is reported where it is decided: an argument overload choice rejected (`resolution/calls/resolve/index.ts`), a struct target naming another type (`constructs/patterns/walk/parts.ts`). Every producer of one value agrees on its type by one rule (`rules/agreement.ts`); `if` and `match` add their branches to it through `constructs/expressions/control/branches.ts`. Lowering's totality property (every program that checks clean compiles into a Definition the runtime loads) ties what the checker accepts to what lowering and the runtime take.

Node kinds are PascalCase, so a table keyed by them sits between `biome-ignore-start` and `biome-ignore-end` comments for `useNamingConvention`, and nowhere else is the rule suppressed.

## State: derive, never mirror

Every analysis result is a memoized function of immutable inputs: text → tokens → tree → Program → bindings → types. Caches are keyed by the input object (a `WeakMap`), so a new snapshot is a new key and nothing is ever invalidated by hand. Every one goes through `memo` (`foundation/structures/memo.ts`), which remembers an `undefined` too, or `SequenceMemo` for a value derived from a sequence of objects, such as a module's items, or, inside one check, `RevisionMemo` for what is read of an inference system, which changes in place and names its state by a revision it bumps at every change, except the checker's, which are entries (`foundation/structures/entries/`): memoized the same way, and each kept with what it read and reported, so a result never depends on the order things were asked in, and a checker made after an earlier snapshot's takes over every result whose reads answer alike, with nothing invalidated by hand. An entry logs each input read once; replaying it re-reads only those. The LSP holds only document texts and derives everything else. The runtime's only state is the instance snapshot.

## Decisions

- **Hand-written scanner and parser** (Pyright/TypeScript style). Rejected:
  - Langium: its indentation lexer can't turn layout back on for a `{}` block inside `(…)`, and Typir has no generics.
  - Chevrotain, Lezer, tree-sitter: they give untyped CSTs, and context-dependent `{` and generic-call speculation would fight the grammar.
- **Inference is constraint-based, and conversions compose through variance** (docs/work/variance-inference/design.md). Identity is read off declarations (`shared struct`; `extern shared`, `sendable` or `live struct`), never off names; a handle is invariant. A value type's variance is derived from its fields, an extern's written (`gives`/`takes`). Each outermost expression is one constraint system (wiring/body/constraint-scope.ts), placed by the scope protocol (wiring/body/scope-protocol.ts): arguments and the expected type give bounds; a generic call, a literal naming its type, or a collection literal passed straight to a call joins it, as does a postponed lambda's value where its result is still open; and one settling policy decides, after which one pass completes and records every construct. Choosing a function never reads the expected type. A literal is never checked twice to be built as another type: it joins, converts (§3.5), or, a `struct{…}`, is decided by where it goes (§3.1). Rejected: the expected type as written type arguments for every call (unsound: candidates depend on the arguments) and Swift-style joint search (backtracking).
- **No DI container.** Explicit composition roots plus registries keep wiring visible and type-checked.
- **Positions are UTF-16 offsets**, the LSP default. They are converted only at the edges.
- **Formatter layout algorithm comes from a library:** Prettier's doc printer (`prettier/doc`, pinned exactly), which formatter/ alone imports. The formatter supplies only the printers from tree to doc and the comment placement (formatter.md, Decisions).
- **Runtime keeps frames as data.** The Definition is linear register code, so a frame is a function, a pc and registers, and any `await` can be persisted (spec §5). Code is untyped, and generics are compiled per instantiation. The chosen and rejected options are in definition.md, Decisions.
- **One description per persisted format.** A zod schema validates, decodes and encodes it; texts are canonical JSON (lossless-json with sorted keys) nested in a `{format, version, body}` envelope, keyed by content hash. The codec and envelope live in `definition/formats/` (`codec.ts`, `format.ts`), the lowest layer every persisted format already depends on; `runtime/` (snapshots, and from M3 the boundary) imports them from there. Values use `bigint` for `Int`.
- **`Decimal` runs on decimal.js,** picked over big.js and bignumber.js because it rounds to significant digits, which `/` needs (34, decimal128's), and has every rounding mode. A `Decimal` is a value of an extern type the `decimal` module declares, whose payload is its canonical text: fields can't be private (spec §3.1), so a struct could be built in a second form, and `==` and map keys would compare forms, not numbers. `time.Zone` is an extern type for the same reason, its payload the zone's canonical IANA id.
- **`regex` runs on re2js,** a pure JavaScript port of RE2: matching is linear in the text, so no pattern can make an instance hang, and RE2's syntax refuses backreferences and lookaround. A regex is its pattern's text, so its compiled program is derived from that text: memoized by it in one bounded, process-wide cache (`lru-cache`).
- **A wait on another instance's end is read from the store** (spec §9). `inst.result()` is a watch future; at each segment start the scheduler resolves it from the watched instance's last commit (scheduler/instance/instance-ends.ts), in every runtime, a test's included, while a test world answers only a test's own waits (`idle()`, `reaches()`), so an outcome is copied snapshot to snapshot and never passes through a host's JSON. What a host must do is only wake the watcher: a waiting `InstanceState` names the instances it watches, and `InstanceGroup` runs a watcher once one of them has ended, after any instance spawned and not yet run. `runtime.isolate` is a spawn with the `terminatesOnPanic` option, kept in the child's snapshot: its panic commits, then terminates it at once, keeping the panic for the `Err`.
- **Static lifetimes' relations are rows of bits** (rules/lifetimes/node-relation.ts, on `typedfastbitset`, pinned exactly). The analysis's relations run dense, and most writes re-add pairs that hold: a set paid a hash per pair, a bitset a word, and Biome refuses hand-written bitwise code. A row a join widens is trimmed back, since the library widens a row to twice the width of a wider row joined into it.
- **Methods taking a function are language code.** A native can't call a function value, since a call never re-enters the interpreter, so the prelude's `map`, `filter`, `sort` and the rest are prelude.ista code, and `collections.WeakMap` is the collections module's.
- **Test capabilities are built into the runtime** (spec §10):
  - Every call goes through one call path, where a mock the calling instance holds, or one an instance it descends from holds, replaces its target. A mock is a heap object, so which mock a call reaches is derived from the holder's heap, and releasing a mock brings back the one before it. A mock replaces a function's body, not its defaults: a call leaving parameters out runs the target's prologue first, then hands over with every argument, the replacement taking the prologue's frame's place (segment/calls.ts), so the replacement and `calls()` see them all and no trace shows the target.
  - A test runs as an invocation into a context of its own, `test` (runtime/testing/world/), its outcome its answer. An instance a test starts calls the test's mocks as it would call a host's extern: the holder runs the replacement inside the caller's segment, and fills the caller's future when a returned future resolves (an `answer` object). One test's instances therefore never share a heap, so `crashEveryAwait` and every snapshot rule hold for them as for any instance. A mock plays the host, in its own instance or another's: a disposable host value it receives or hands back stays a plain host value there, so only the caller owns and disposes it.
  - An advance ends at a commit that answers another instance's call, so the answer arrives, and its caller runs, before the holder goes on; while a caller's segment waits on an answer, no watch sees it idle or at a waypoint.
  - After every commit, the world has each holder drop its answers to calls whose futures the committed caller no longer has (an advance starting `withdrawn`), so what they wait on is let go: a mocked receive that loses a `select` takes nothing, as §6 says.
  - `handle<T>()`, a test's own watches on a spawned instance (`idle()`, `reaches()`) and its reads (`waitingAt()`, `state()`) are runtime capabilities (`NativeTesting`); spawning with `crashEveryAwait` is the production capability `NativeInstances`, as `result()` and `isolate` are. A panic some instance waits for through `result()`, as `expectPanic` does, fails no test. What a test reads of another instance is that instance's last commit, through the test world (scheduler/testing/test-world.ts), which `runtime/testing/` gives each test (and `noTestWorld` refuses outside a test).
  - `ista test` is a CLI command over `runtime/testing/`; the test library is the `testing` std module, written in the language. A suite function is called again in each test's instance, and `_list`/`_run` (testing.ista) are the one place a suite's tests are flattened.
  - A test module sees the private declarations of the modules it imports (binder), so a test can mock a raw extern a module wraps.
