# 8.1 Generics

Structs and functions take type parameters in angle brackets. Type arguments can always be written explicitly at a call site. Otherwise they are inferred, as in Kotlin: each argument fits its parameter as any value fits (§4.1), and where a type parameter stands, what fits there bounds it. What the parameter is given bounds it below, what it gives, a function type's parameter, bounds it above, and where a value must have the type exactly, an invariant type argument (below), a `&` or a spread's items, it must be that type. A struct's fields fill a shape (§5.2), so `fn f<T>(p: { x: T, y: T })` called with a `struct Pixel { x: Int, y: Int }` gives `T` an `Int`. Against a union holding type parameters, an argument fills them with what the union's other members don't take (§4.2): `fn f<T>(x: T?)` called with an `Int` or an `Int?` gives `T` an `Int`, and called with `none`, or any `None` value, gives it nothing. A written literal gives its literal type, widened to its base below unless a literal type of that base bounds the parameter above. A method's receiver gives its type parameters exactly, as Swift and Rust bind `Self`, so `xs.includes(none)` for an `Array<Int>` is an error, never a reason to widen `xs`. A value converted into an `any` type relates through the one instantiation of each of its traits that its type may meet, as its witnesses' signatures say, related as that trait's variance says (§8.3): `fn takes<S>(v: any View<S>, s: S)` called with a `LayoutView<Scope>`, whose `draw` takes a `Scope`, gives `S` the `Scope`, and a `LayoutView{…}` written where an `any View<Scope>` is expected gives its own `S` the same. A witness declared for one instantiation (`fn draw(self: Box<Scope>, s: Scope)`) makes a `Box{…}` that instantiation. Where several relate, it gives nothing, and whether the value meets the one its type arguments settle to is judged once they are known. Once the function is chosen, the type the call is expected to have bounds its result alike, but only advises: where it disagrees with the arguments it is set aside, and the call's value is judged against it as any value is. Each type parameter then settles on the first of:

1. the type it must be exactly;
2. inside the result, the choice of what takes the call's value, its expected type or the parameter of a call it is passed to, where every other bound and the parameter's constraints agree, so a value is built at the type it goes to: `pair(1, 2)` expected as an `Array<Int?>`, or passed to a `fn takeArr(xs: Array<Int?>)`, builds an `Array<Int?>`. At the result's top, the result itself or a member of it, the call's value converts instead, wherever the call stands, so both branches of `if c: id(1) else: id(2)` expected as an `Int?` give `T` an `Int`: `biggest(a, b)` expected as an `Int?`, for `fn biggest<T is Comparable>(a: T, b: T) -> T`, gives `T` an `Int`;
3. the common type of what it was given (§4.2), which no upper bound refuses: one of them that holds the others, else a type with `None` joined into its optional;
4. an upper bound every other bound agrees with, a written union among them: `pick("draft", "sent")` expected as a `Status` gives `T` the `Status`;
5. its default.

A parameter left with none, or given types that disagree, which inference never joins into another union, is a compile error that asks for the type arguments.

**One expression, one inference.** A generic call, a literal naming its type, or a collection literal passed straight to a call doesn't settle alone: its type parameters are inferred together with the call's, the outermost expression's settling them all, as Kotlin does. So what the outermost call is expected to be, and what its other arguments give, reach what is nested in it: `items([Item{value: "s"}])` expected as an `Options<"s" | "m">` builds an `Array<Item<"s" | "m">>`, `boxed(Ok(5))` expected as a `Box<Result<Int?, String>>` gives `Ok` its `Int?` and `String`, and `pair(id(1), id(none))` is an `Array<Int?>`. A variant's call is such a call (§5.3). One whose result is computed from its own type parameters, an associated type or a field's type, has those settled first by what it is given, a lambda passed to it checked first, since nothing it is passed to can tell them through a computed type: `text(scopeOf(f))` for `fn scopeOf<N is Node>(n: N) -> N.Scope` gives `text`'s `T` what `N.Scope` reduces to. A call choosing among functions reads what only a default decides of what it is given as that default, as it will settle: `pickArr(empty())` for `fn empty<T = Int>() -> Array<T>` takes the `pickArr` of an `Array<Int>`, where with no default it is ambiguous. A lambda's body is checked once what its parameters are given is settled, guided by what is expected of its result; where that is still open, its value joins the call too: `f(fn x: Good(x + 1))` for `fn f<U>(g: fn(Int) -> Outcome<U, String>)` gives `Good` its enum and `String`.

```ista
struct Pair<A, B>:
    first: A
    second: B

fn swap<A, B>(p: Pair<A, B>) -> Pair<B, A>:
    Pair{first: p.second, second: p.first}
```

- **Explicit type arguments** use the same brackets everywhere: `swap<Int, String>(p)`, `Slot.create<Verdict>()`, and after a function named as a value, `listed<Int>` (§6.4). Trailing ones that have defaults may be left out.
- **Defaults.** Any type parameter may have a default, on a struct, enum, trait, alias or function alike: `enum Result<T, E = Error>`. A default fills a type argument that is neither written nor inferred.
- **Parsing.** In an expression, a name or qualified name followed by `<...>` takes type arguments when the part inside the brackets parses as a list of types whose names all start with a capital, as types' do and no variable's does (§4.1), and what follows can't go on with a comparison: a `(` or `{` on the same line, its call or a struct literal (`swap<Int, String>(p)`, `Pair<Int, String>{first: 1, second: "x"}`); a token no expression starts with, such as `)`, `,`, `]`, `==` or the line's end, but not the rest of a `>>` or `>=` whose `>` closed the brackets; or the next item of a list broken over lines (§2.1). Without a call it is the function given those type arguments, named as a value (§6.4): `xs.map(Result.Ok<Int, String>)`. So `f(a < b, c > d)` and `f(a < b, c > (d))` hold two comparisons of variables, and so does `f(a < B, C > d)`, whose `d` goes on after the `>`. Literal types, unions and a field's type by key are types, so `a < 1 > (b)`, `a < B | C > (d)` and `a < B["c"] > (d)` are calls. A comparison that looks like type arguments needs parentheses: `(a < B) > c`.
- **When inference has nothing to go on,** give the type arguments or annotate the variable: `let xs: Array<Int> = []`.
- **Constraints.** A type parameter can be constrained by traits (§8.2) with `is`: `T is Sendable`. Several traits are joined with `&`: `T is Sendable & Comparable`. Every type argument, written or inferred, is checked against its parameter's constraints wherever it appears: in a call, an annotation or a literal.
- **Struct constraints.** After `is`, `struct { … }` constrains a struct's fields: `S is struct { title: String, [_] is FormNode }`. Only a struct type meets one: a struct declaration's, not a shared or extern struct's, or an anonymous struct type (§5.2). `name: Type` requires the field with exactly that type, after aliases; `name is C` requires it to meet `C`, traits joined with `&` or a struct constraint; `[_]: Type` and `[_] is C` do the same for every field the constraint doesn't name, one such entry at most. A struct may have fields the constraint doesn't name. Inside the braces `&` constrains each field, outside it the parameter: `T is struct { [_] is A } & Sendable`. Bare `struct` is met by any struct. A recursive struct type (§5.2, §4.6) meets one when its fields do, assuming the struct itself meets it while its fields are checked. A type parameter meets one when its own struct constraints imply it: they name each field it names, with an entry implying that entry, and, when it constrains the other fields, every field they name beyond its own and every field their `[_]` entries cover meets that; so `S is struct { a: Int, [_] is Stringable }` meets `struct { [_] is Stringable }`, since `Int` meets `Stringable`. A struct constraint is never a type: it stands only after `is`.
- **Checked once.** A generic body is checked once, not per instantiation: inside it, a value of a type parameter supports only what the parameter's constraints require, plus `==`. A struct constraint's named fields are read and written by name, `t.title`, typed as their entry: the exact type, or an opaque type meeting its constraints; its other fields are out of reach. An associated type of a type parameter, `T.Data`, is opaque too, equal only to itself (§5.2), and so is a use of a type `match` its type parameters don't decide yet, equal only to the same alias with the same arguments (§4.6). Using a generic function therefore never reports an error inside its body.
- **Inference never goes through an associated type or a type `match`:** `fn f<T>(x: Field<T>.Data)` is called `f<Int>(x)`, and `fn g<D>(x: DataOf<D>)` is called `g<OrderForm>(x)`, or with another argument, or an expected result, that gives the parameter.
- **Packs.** A function's type parameter written `<...A>` stands for a tuple of types, so one declaration takes any number of arguments of any types. It is used as a rest parameter, `...args: A`, as the rest of a function type, `fn(Int, ...A) -> R`, and anywhere a tuple type can stand, such as `Array<A>`. Substituting a tuple for it flattens a rest: `fn(...A)` with `A` as `(Int, String)` is `fn(Int, String)`, and with `()` is `fn()`. A pack is inferred from the arguments its rest parameter collects, as the tuple of their types, or from a function argument's parameters (`logged(area)` binds `A` to `(Int, Int)`); written, it is a tuple type: `logged<(Int, Int), Int>(area)`. Inside its function a pack is opaque: a value of it can be passed, kept and compared with `==` as any type parameter's, and spread with `...` only where a rest of the same pack takes it, as `f(...args)` does. The arguments a pack's rest collects are single values by position, or one such spread; nothing names them. A pack takes no constraint and no default, a struct, enum, trait or alias takes none, and a function has one rest, an array or a pack.
- **Member parameters.** A type parameter written `<S in U>` stands for exactly one member of the union `U`, never several; `U` may mention earlier parameters, but is no member parameter, which stands for one type already (`<S in S>` and `<A in B, B in A>` are errors). An argument whose type is one member of `U` fills it, a literal with its literal type (§4.3): `describe("draft")` below binds `S` to `"draft"`; a literal type whose base is a member fills it with that base. An argument whose type is a union of several members doesn't, a compile error as for overloads (§6.3): narrow it first, with a literal or type pattern (§11.3). A type argument written for it, to a call or to a type, is one member too, or a member parameter whose own union's members all are, never a type parameter that could be any type: `Entry<T>` is an error for an unconstrained `T`, and `Entry<K>` checks for `K in Status`. The body is checked once, with `S` known only to be one member of `U`, so its values fit `U`; each member it is used with is its own instantiation. A value of `S` compares by `==` and literal patterns (§11.3) as that member: with any literal of its base, always unequal to one no member equals, a condition decided by types (§11.1), and cases covering each literal member of `U` cover `S`. Declarations take one as functions do, `struct Entry<V, K in Status>`. It takes no `is` constraint beside its union, and its default, if any, is one member: `Kind in Mark = "simple"`. One whose members are each a literal type is also a value where a body names it, that member's one value, as a struct with no fields is its own (§5.2): `fn describe<S in Status>() -> String: S` reads `S`, and so does a loop's key over a type's keys (§11.2). One with a member holding more values, `S in String`, is no value.

- **Variance.** Each type parameter of a struct, an enum or an extern struct says how the type's instantiations relate. A **covariant** one only gives its values out, so `X<A>` fits where `X<B>` is expected when `A` fits `B`: an `Array<Int>` is an `Array<Int?>`, and `Box<"s">` a `Box<String>`. A **contravariant** one only takes them in, so it goes the other way: a `Sink<Int?>` is a `Sink<Int>`. An **invariant** one does both, so the two must be the same type. Conversions compose this way (§4.1), rebuilt where a value's layout changes: an `Array<Int>` into an `Array<Int?>` wraps each item, a `Box<"s">` into a `Box<String>` stays as it is.
  - A struct's or an enum's is derived from where it occurs in what its values hold: a field is covariant, a function type's parameter flips the direction (`fn(T) -> Unit` takes a `T` in), an `any` type's constraint passes it on as its trait's variance says (§8.3), and a handle's type argument, a `&`, an associated type, a field's type by key, `keyof`, a mapped type and a type `match` make it invariant; one occurring nowhere is covariant. A member parameter (`S in U`) is invariant, each member being its own instantiation. Written before it, `gives` (covariant) or `takes` (contravariant) asserts what it derives, a compile error where it doesn't (`struct Sink<gives T> { take: fn(T) -> Unit }`).
  - An extern value's is written, since nothing derives it: `extern struct Array<gives T>`, `extern struct Map<K, gives V>`; one written with neither word is invariant. `gives` promises the runtime rebuilds a value at a wider argument, which a host's values meet by their JSON reading alike.
  - A handle's are invariant (§7.2, §5.4): a value put in through one copy is read through every other, so a `Slot<Int>` is no `Slot<Int?>`, and neither word is written on one. A function's, a trait's and an alias's type parameters take neither: each call infers a function's, a trait's are derived where it is used through `any`, and an alias is the type it names. A one-element tuple converts into its element, and back, only as a whole value (§4.5).
- **Compiled per instantiation.** A generic function or type is compiled once for each set of concrete type arguments it is used with, so every call has a fixed target and the runtime never needs types to make one (§8.2). A generic function or type that would need endlessly many instantiations, such as `f<T>` calling `f<Array<T>>`, or `struct W<T>` with a field of type `W<(T,)>?`, is therefore a compile error, and so is a type `match` reducing to itself that way, `W<T>` to `W<Array<T>>` (§4.6).

```ista
fn logged<...A, R>(f: fn(...A) -> R) -> fn(...A) -> R:
    fn(...args: A) -> R: f(...args)          # wraps a function of any parameters

fn area(width: Int, height: Int) -> Int: width * height

fn measured() -> Int:
    const measure = logged(area)             # A is (Int, Int): fn(Int, Int) -> Int
    measure(3, 4)
```

```ista
type Status = "draft" | "sent" | "failed"

fn describe<S in Status>(s: S) -> String:    # one instantiation per member used
    `status ${s}`

fn report(status: Status) -> String:
    match status:
        case "draft" as d: describe(d)        # d: "draft"; describe(status) is an error
        case _: describe("sent")
```
